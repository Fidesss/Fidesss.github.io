Troubleshooting

회원 · 인증 트러블슈팅

01 · 배포 환경에서 로그인 토큰이 쿠키에 저장되지 않는 문제 cookie · CORS

상황
로컬에서는 정상이던 로그인이 배포 후에는 JWT 토큰이 쿠키에 실리지 않는다는 제보를 프론트엔드 팀원에게서 받았습니다.
확인
CORS 설정, 프론트엔드의 쿠키 설정, 백엔드의 쿠키 생성 코드, Spring Security 설정을 차례로 점검했습니다.
원인
프론트엔드와 서버의 주소가 달라 브라우저가 크로스 사이트 요청의 쿠키를 받아들이지 않았습니다. 이 경우 SameSite=None과 Secure를 함께 지정해야 하는데, 기존에 사용하던 서블릿 Cookie로는 SameSite를 지정할 수 없었습니다.
조치
쿠키 생성을 Spring ResponseCookie로 바꿔 HttpOnly · Secure · SameSite를 함께 지정하고, 로그아웃용 쿠키 삭제 메서드도 같은 방식으로 정리했습니다.
결과
원인을 찾아 SameSite를 지정할 수 있는 방식으로 쿠키 생성 코드를 바꿨습니다. 다만 로컬(HTTP)과 배포(HTTPS)의 쿠키 설정 값이 달라 코드를 여러 번 고쳐야 했고, 이 경험으로 환경마다 달라지는 값은 설정 파일로 분리해야 한다는 점을 배웠습니다. 15da510 · e50f5a5 · db91b73

02 · 소셜 로그인 공급자마다 응답 구조가 달라 로그인이 실패하는 문제 OAuth2

상황
구글 로그인을 먼저 구현한 뒤 카카오와 네이버를 추가하는 과정에서 공급자마다 다른 오류가 발생했습니다.
원인
구글: 카카오에 맞춰 사용자 식별 속성을 id로 고정하자, id 값이 없는 구글 응답에서 로그인이 실패했습니다. 카카오: 토큰 요청에서 401 [no body]가 발생했고, 클라이언트 시크릿 설정이 맞지 않는 것이 원인이었습니다. 네이버: 사용자 정보가 response 안에 한 번 더 감싸져 있어 이메일을 찾지 못했습니다.
조치
OAuth2UserInfo 인터페이스와 공급자별 구현체(Google · Kakao · Naver)로 응답 파싱을 분리하고, 사용자 식별 속성도 공급자별로 지정했습니다. 지원하지 않는 공급자는 커스텀 예외로 처리했습니다.
결과
세 공급자의 로그인을 하나의 서비스 로직으로 처리하게 되었고, 새 공급자는 구현체만 추가하면 되는 구조가 되었습니다. 0af0678 · 762f1ee · 33f9b4b
