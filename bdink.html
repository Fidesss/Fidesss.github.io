RAG를 사용한 AI 운동 메모 openai · RAG

배경
운동할 때마다 버튼을 반복해서 눌러야 하는 운동일지 기록 방식을 개선하기 위해, 자유롭게 쓴 메모("랫풀다운 70 80 80 / 8-12reps")를 운동명 · 세트 · 중량 · 횟수로 바꾸는 기능을 만들었습니다. LLM에 그대로 맡기면 DB에 없는 운동명을 지어내거나 JSON이 깨졌습니다.
접근
운동 종목과 별칭을 OpenAI 임베딩으로 벡터화해 PostgreSQL pgvector에 저장(주 DB와 데이터소스 분리)했습니다. 메모를 줄 단위로 나누고 숫자 · 단위를 지운 뒤 임베딩해 코사인 거리로 후보를 추리고, 그 후보 목록만 프롬프트에 주입해 LLM이 목록 안에서만 고르도록 제한했습니다.
도구
AI 코딩 도구 Codex로 기존 코드 분석과 단계별 구현을 진행하되, 모든 변경에 주석과 이유를 요구하고 LLM 응답을 로그로 확인하는 JUnit 테스트로 결과를 검증했습니다.
결과
약 3주에 걸쳐 개발해 서비스에 적용했습니다(PR #426). 입력은 이메일 · 전화번호 마스킹과 SHA-256 해시로 기록해 실패 케이스를 추적할 수 있게 했습니다. gpt-4.1-mini · text-embedding-3-small

01 · 여러 운동을 한 번에 입력하면 일부가 빠지는 현상 RAG

상황
iOS 개발자와 실제 앱으로 대면 테스트하던 중, 메모에 운동을 여러 개 쓰면 일부가 결과에서 빠지는 것을 발견했습니다.
원인
메모 전체를 한 번에 임베딩해 검색하면 한 운동의 의미가 다른 운동에 묻혀 상위 후보에 들지 못했습니다. 후보가 많아질수록 LLM이 선택을 빠뜨리기도 했습니다.
조치
줄바꿈 · 쉼표 · ; · |로 나누고 숫자 블록 뒤에 새 단어가 시작되면 다른 운동으로 분리했습니다. 줄마다 따로 임베딩 · 검색하고, 줄 수에 따라 후보 수를 조절(2줄 이하 10개, 그 이상 7개)했으며, 줄마다 1순위 후보는 거리 기준과 관계없이 포함했습니다. LLM이 운동 ID를 비워 두면 그 줄의 1순위 후보로 대체했습니다.
결과
여러 운동이 섞인 메모도 운동 단위로 변환됐고, 대체 동작은 LLM exerciseId missing. Fallback to RAG top1 로그로 추적할 수 있게 되었습니다. 0203ac3 · 48f909e

02 · 성공 응답인데 결과가 비어 있는 현상 RAG

상황
API는 201을 반환하는데 sessions: []로 비어 있거나 운동 ID가 null로 내려왔습니다.
확인
운동이 사라질 수 있는 지점을 검색 → 거리 기준 → LLM 선택 → ID 매핑 네 단계로 나누고, 단계마다 로그(RAG candidates, after threshold)를 남겨 추적했습니다.
원인
새 pgvector DB에 임베딩이 0건이었습니다. 백필 작업이 MySQL에 벡터가 이미 있으면 건너뛰기 때문입니다. 거리 기준이 엄격해 후보가 모두 걸러지는 경우도 있었습니다.
조치
OpenAI를 다시 호출하지 않고 MySQL 벡터를 pgvector로 복사하는 동기화 작업을 백필과 분리했습니다. 거리 기준값을 조정하고, 프롬프트에 "후보 이름 · 별칭이 입력에 포함되면 반드시 선택" 규칙을 추가했습니다.
결과
운동이 정상적으로 매핑됐고, 같은 증상이 나와도 로그만으로 어느 단계의 문제인지 특정할 수 있게 되었습니다. 3093c4e

03 · 벡터 쿼리가 MySQL에서 실행되는 문제 멀티 데이터소스

오류
You have an error in your SQL syntax near '::vector' 오류가 발생했고, 스택 트레이스에는 MySQL JDBC 클래스가 찍혀 있었습니다.
원인
pgvector용 JdbcTemplate에 데이터소스를 지정하지 않아 기본 MySQL이 주입됐습니다. 같은 이유로 MySQL JPA가 vector(1536) 컬럼 생성에 실패했고, url이 HikariCP의 jdbcUrl로 바인딩되지 않았습니다.
조치
@Qualifier("pgvectorDataSource")로 주입 대상을 명시하고 기본 JPA는 MySQL로 고정했으며, 벡터 스키마는 PostgreSQL에서만 관리하도록 분리했습니다.
결과
시작 로그에서 두 커넥션 풀이 각각 의도한 DB에 연결되는 것을 확인했습니다. b8c42d9

04 · 임베딩 저장 작업에서 발생한 오류 RAG · DB

오류
Connection is read-only, no unique constraint matching the ON CONFLICT, Data too long for column 오류가 차례로 발생했습니다.
조치
백필을 쓰기 트랜잭션으로 바꾸고, 업서트 기준인 exercise_id에 유일 인덱스를 추가했습니다. 1536차원 벡터와 긴 메모 로그 컬럼은 LONGTEXT로 바꿨으며, 이미 임베딩된 운동은 건너뛰어 중복 호출을 막고 코사인 거리용 HNSW 인덱스를 구성했습니다.

05 · 테스트 영상조차 S3에 올라가지 않는 문제 영상 · S3

상황
퇴사한 팀원이 만든 멀티파트 업로드 코드를 강의 서비스에 연결하던 중, 짧은 테스트 영상도 S3에 저장되지 않았습니다.
확인
권한 · 주소 · 영상 길이를 의심했고, S3 콘솔에서 파일이 없는 것을 확인한 뒤 업로드 시작 → 조각 업로드 → 병합 요청 흐름을 코드로 단계별로 따라갔습니다.
원인
반복문에서 조각 정보를 만들기만 하고 리스트에 추가하지 않아, 병합 요청의 조각 목록이 비어 있었습니다. 또한 업로드 ID를 영상 ID로 쓰고 있어 변환 경로와 재생 주소가 어긋나 있었습니다.
조치
조각 목록을 수정하고, 영상마다 UUID를 발급해 파일명 · 저장 경로 · 재생 주소를 통일했습니다. 바뀐 흐름은 Notion으로 앱 개발자와 공유했습니다.
결과
2일에 걸쳐 해결했고, 업로드부터 재생까지 하나의 영상 ID로 연결되었습니다. fa73368 · PR #461

06 · Kollus 재생 콜백을 파싱하지 못하는 문제 외부 연동

상황
Kollus의 재생 콜백을 받아 시청 진행률을 저장해야 했는데, 콜백 수신과 파싱이 실패하고 진행률도 반영되지 않았습니다.
원인

조치
실제 요청을 기준으로 kind별 DTO를 나눠 처리했습니다.
배운 점
외부 연동은 문서보다 실제 요청이 기준이라는 것을 배웠습니다. 가설을 바꾸기 전에 확인용 로그로 실제 데이터를 먼저 보는 습관을 갖게 되었습니다.

08 · 푸시 알림이 실패하거나 표시되지 않는 문제 FCM

401
서버의 서비스 계정 인증이 거부됨 → 실제로 읽은 키 파일 경로, 토큰을 발급한 프로젝트와 project_id 일치 여부, 발송 권한, Cloud Messaging API 활성화를 점검했습니다.
400
서버에 저장된 값이 FCM 토큰이 아니라 기기 식별자였음 → 앱이 Firebase SDK로 받은 토큰을 등록하도록 앱 개발자와 규격을 정하고, 앱 시작 · 로그인 · 토큰 갱신 때 다시 등록하도록 했습니다.
404
앱 삭제 등으로 무효가 된 토큰 → 재시도하지 않고 비활성화했습니다.
표시 안 됨
서버 성공은 FCM이 요청을 받았다는 뜻일 뿐임 → 알림 payload에 title · body를 추가하고, 앱의 포그라운드 처리 · 알림 권한 · APNs 설정은 앱 개발자와 나눠 점검했습니다.
배운 점
"초기화 성공", "발송 성공", "기기에 표시됨"은 서로 다른 단계이며, 단계를 나눠 봐야 문제 위치가 보인다는 것을 배웠습니다.

결과

수강 신청 · 조회, 클래스룸별 학습 진행률 응답, 만료일 자동 스케줄러, 중복 처리.

center 신규 구축

센터 도메인

센터 CRUD, 강사–센터 연관관계, 센터 · 클래스룸 QR 코드 발급 · 검증(zxing).

trainer · trainermembership 신규 구축

트레이너 · 구독 도메인

트레이너 · 센터장 · 소속 CRUD, principal 기반 담당 회원 조회, 회원 운동일지 조회와 피드백. 구독은 결제 직후 트레이너 · QR 자동 생성 → S3 업로드, 만료 스케줄러로 구성했고, subscription → trainermembership 패키지 · 스키마 정리를 주도했습니다.

notification 설계·구현

알림 · FCM 푸시

알림 엔티티 · 타입, soft delete, 안 읽은 알림 조회. 도메인 이벤트(QR 등록, 피드백, 수강 신청, 답변)별 알림 생성을 NotificationFactory로 통합. FCM 기기 토큰 관리, 딥링크별 푸시, 휴면 전환 시 토큰 비활성화.

learning 설계·구현

학습 진행률

LearningProgress(강의별 최대 진도 · 완강 상태)와 LearningProgressEvent(PLAY · HEARTBEAT · SEEK 등 원본 로그) 엔티티, 클라이언트 보고형 진행률 조회 · 저장 API. Kollus 콜백에 의존하던 클래스룸 · 수강 진도 집계를 이 엔티티 기준으로 전환.

global 공통 유지관리

공통 · 인프라

표준 응답 포맷(Success / Error enum) 관리, Discord Webhook 자동화와 테스트, 운영 · 개발 Swagger 분리, 멀티 데이터소스 설정, CoolSMS 인증 만료 검증.

Architecture

구조화 관점 기여

관점내용
도메인 분리신규 도메인 설계 — workout, openai, center, trainer*, notification, learning
외부 연동 격리서드파티 연동을 external/* 패키지로 캡슐화 (Kollus 등)
영상 소스 이관외부 플랫폼(Kollus)에서 자체 AWS(CloudFront HLS)로 이관 — 강의 도메인 교체 · CDN URL API · 진행률 재설계 담당
데이터소스 분리RAG용 pgvector를 주 트랜잭션 DB와 분리된 데이터소스로 구성
흐름 설계결제 → 트레이너 / 구독 / QR 자동 생성으로 이어지는 흐름 설계
알림 통합도메인 이벤트 → NotificationFactory 패턴으로 생성 지점 일원화
